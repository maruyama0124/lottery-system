# メンバーホームの初期表示検証（2026-10-13）

macOSのChrome headlessで、実際のNext.js画面を起動して計測した。本番のLINE・API・DBは呼ばず、ブラウザのAPI通信だけを合成データへ置き換えた。Next.js開発サーバーと静的アセットを一度ウォームアップしてから、各条件を3回計測して中央値を比較した。「初回」は端末のデータキャッシュなし、「再アクセス」は同じユーザーでページを再読み込みした場合である。静的アセットまで空にした初回起動や本番速度を測ったものではない。

通信条件はブラウザ→BFFの往復200ms、順番に必要になるバックエンド取得段階あたり50msで固定した。従来の個別APIを250ms、一括取得APIを300msで応答させる。時間はURLへの移動から日程・公開結果の体育館名がDOMへ表示されるまで（約50ms間隔の検出、描画時刻も利用）である。

| 表示内容 | アクセス | 変更前 | 変更後 | ブラウザ→BFFのAPI回数 |
|---|---|---:|---:|---|
| 公開済み結果 | 初回 | 1,314ms | 1,128ms | 6 → 2 |
| 公開済み結果 | 再アクセス | 1,331ms | 825ms | 6 → 2 |
| 投票受付中の日程 | 初回 | 1,324ms | 1,124ms | 5 → 2 |
| 投票受付中の日程 | 再アクセス | 1,337ms | 845ms | 5 → 2 |

表示時間はこの条件で初回約14〜15%、再アクセス約37〜38%短縮した。再アクセスにも認証確認1回と裏での更新確認1回が含まれる。時間の短縮は保存済みの日程・結果を先に描画し、APIごとのブラウザ往復を減らす効果である。BFFからバックエンドへ必要な取得は残る。通常の公開月はBFFの一括取得で5回、未公開の本人月は4回（別途初期認証1回）であり、SQL実行回数の削減を証明する測定ではない。LINEログイン後の認証情報の受け渡しは再度の `/api/auth/me` を必要としない。

ブラウザで次も確認済みである。

- 投票の編集中に更新確認が完了しても選択を上書きしない。
- 投票保存後のキャッシュ無効化・再取得でも、保存した選択を戻さない。
- 更新確認に失敗すると古い情報である旨と再試行が表示され、再試行成功後に解消する。
- 有効なセッションで `/line` を開くとLINEログインAPIを呼ばず、ホームへ進む。

再現コマンド（frontendディレクトリで実行。macOS版Chromeが必要）：

```bash
node tests/measure-member-home.mjs before http://localhost:3102 551285913cda7da6cc13f076dbbf9300bb47bba6
node tests/measure-member-home.mjs after http://localhost:3101
npm run test:results
```

測定スクリプトは一時コピーを作成し、既存の開発サーバーとは異なるポートで起動する。認証CookieもAPI応答も検証用のダミーであり、DBへの保存は行わない。

本番への反映後はChromeのNetworkで「ログを保持」を有効にし、認証済みの同じアカウントでキャッシュなし／ありを比較する。`/api/auth/me` と `/api/member/home` の2通信、画面の更新確認表示、Vercelの `[timing] member_home` に出る `backendRequests / totalMs` を確認する。認証情報を含むCookie・HARは公開しない。公開が取り消された以前の公開スナップショットは、再取得によって非公開化を確認するまで古い情報として表示され得る。
